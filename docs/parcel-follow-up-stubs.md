# Parcel follow-up tasks: queue-only stub

**Delivery boundary.** This implements private follow-up tasks and a real PostgreSQL reminder-intent queue. It does not provision EventBridge, call AWS, send SMS, collect phone numbers, or complete V1 SMS delivery. Tasks are not owner outreach. The buyer's own message is private and never included in API logs.

**Workflow.** Use the selected parcel Tasks tab to create a personal task for any stored parcel, without favoriting it. First task creates a nonfavorite private tracking record; it never adds a board card or changes the star. `/tasks` contains the paged upcoming and overdue queue; `/leads` remains the saved-parcel board with an Add task action linking to the selected parcel Tasks tab. Removing a favorite preserves open tasks and reminders. Completing or clearing one task cancels only its still-queued reminder; confirmed Clear all atomically cancels the current open tasks and their queued current reminder versions for the selected account and parcel. Completed tasks stay completed. Clear all requires a count from `GET /api/me/parcels/{parcel_id}/tasks/clear`; `POST` sends `{"count":N,"snapshot":"..."}`. Under the account lock the count and exact open-task ID/revision snapshot must still match (1–5000 open tasks), otherwise nothing changes. New tasks or changed task revisions before the lock invalidate the confirmation, even when the count stays the same; creations after commit remain open. Excluding a lead still cancels pending reminders and blocks new task creation and schedules; restoring does not reactivate canceled intents. Stub notices never send SMS.

**Trigger.** On a due, account-owned, open, non-excluded task, press **Simulate SMS (not sent)** in its parcel pane or `/tasks`. This calls `POST /api/me/parcels/{parcel_id}/tasks/{task_id}/stub` with `{"revision": N}`. The authenticated API locks the account and task, rechecks current status, version, exclusion, and atomically transitions the current queued row to `stubbed` (or `missed` if more than one hour past due). It logs `sms-stubbed-not-sent` or `sms-missed-not-sent` with only stable task/parcel IDs, due UTC and version. It never contacts AWS or a carrier. Duplicate or stale calls return 409; an early call returns 400. There is **no automatic trigger**, no timer, no scheduled consumer, and no silent consumption of due intents. A queued row persists after due time until explicit simulation, cancellation or rescheduling. Missed simulation leaves task open for explicit reschedule. Browser clicks operate only on the authenticated account's tasks.

**API.** `POST /api/me/parcels/{parcel_id}/tasks` creates with a client UUID idempotency token and `{id,message,due_at,timezone}`. `due_at` is an RFC3339 local timestamp with explicit numeric offset and `timezone` an IANA identifier; server rejects an offset inconsistent with the zone, including nonexistent DST hours. Ambiguous DST hours require choosing one of two offsets. The server stores UTC. `POST /api/me/parcels/{parcel_id}/tasks/{task_id}/reschedule` takes `{revision,message,due_at,timezone}` and creates an explicit new version; `/complete`, `/cancel`, `/stub` take `{revision}`. `GET /api/me/crm/tasks` and `GET /api/me/parcels/{parcel_id}/tasks` use a bounded cursor (default 20, maximum 50), due-time ordering and only open tasks. `GET /api/me/parcels/{parcel_id}/tasks/{task_id}` reads task status even after completion. All writes require authenticated exact-origin JSON, and guessed foreign IDs do not disclose tasks. API log schedule/cancel entries are operational stub notices, not a durable audit trail; the database queue is authoritative even if process logging fails after commit.

**Message limit.** The editor and server enforce one GSM-7 160-septet segment (extension characters use two septets), or 70 UTF-16 units for Unicode (supplementary characters use two). No text is added, truncated, or actually sent. This limit has not been verified against a selected AWS SMS product. Production delivery still requires verified buyer US destination and consent, sender registration and opt-out requirements, selected AWS product/runtime, claim/retry/uncertain-acceptance design, provider tests and due-time measurements. None is implied by simulated status.

**Verification boundary.** Use an isolated, migrated disposable PostGIS database for `go test -tags postgres -race ./internal/parcelcrm`; set `CRM_TEST_DATABASE_URL` explicitly to its URL. Browser evidence uses Playwright route fixtures and does not verify the live API or real SMS. Do not run the tests against an operator or county database.
